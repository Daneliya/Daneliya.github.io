JDK25 新特性 ​

JDK 25 于 2025 年 9 月 16 日正式发布，是继 JDK 8、11、17、21 之后的又一个 LTS（长期支持版）。它一共包含 18 个 JEP，既有多项语言特性的"转正"，也有并发、JVM、JFR 方面的重要增强。

JDK 25 的一大特点是：前几个版本反复预览的语言特性集中落地。灵活构造函数体、模块导入声明、紧凑源文件和实例 main 方法、作用域值都在这个版本转为正式特性，日常写代码的体验会有明显变化。

一、语言特性 ​

JEP 513：灵活构造函数体（正式） ​

在 JDK 25 之前，构造器中 super(...) 或 this(...) 必须是第一条语句。这带来一个很实际的痛点：父类构造器调用之前无法校验参数。

以 BigInteger 为例，如果想构造一个"正整数"，只能这样写：

java
public class PositiveBigInteger extends BigInteger {
    public PositiveBigInteger(long value) {
        super(Long.toString(value));   // 必须先调用父类构造器
        if (value <= 0) {              // 校验只能放在后面，父类已经执行完了
            throw new IllegalArgumentException("non-positive value");
        }
    }
}

父类构造器已经跑完才发现参数非法，既浪费又可能产生副作用。JDK 25 允许在显式构造器调用之前写语句：

java
public class PositiveBigInteger extends BigInteger {
    public PositiveBigInteger(long value) {
        if (value <= 0) {
            throw new IllegalArgumentException("non-positive value");
        }
        super(Long.toString(value));
    }
}

前置语句并不是毫无限制的，核心规则是 不能引用正在构造的实例：

  • 不能读取实例字段，不能调用实例方法；
  • 不能把 this 作为参数传递或返回；
  • 不能读取尚未初始化的 final 字段；
  • 例外：允许对当前类中声明、且没有初始化器的字段做简单赋值，例如：
java
public class Point extends Shape {
    private final int x;

    public Point(int x) {
        this.x = x;    // 允许：super() 之前给本类字段赋值
        super();
    }
}

需要特别注意：只有显式写出的 super(...)/this(...) 才能被放到语句之后。如果省略了构造器调用，隐式的 super() 仍然被视为构造器的第一个动作。

这个特性最典型的用途就是把参数校验、参数归一化提前，让对象在父类构造完成之前就保证合法。

JEP 511：模块导入声明（正式） ​

JDK 9 引入模块系统之后，使用第三方库时经常需要写一长串 import。JDK 25 新增了模块级导入语法：

java
import module java.base;
import module java.sql;

void main() {
    var names = new ArrayList<>(List.of("Java", "Kotlin"));
    names.addFirst("Scala");
    IO.println(names);

    var conn = DriverManager.getConnection("jdbc:...");
}

import module M; 会导入模块 M 导出的所有包，以及 M 通过 requires transitive 传递依赖的模块所导出的包。例如 import module java.sql; 会顺带引入 java.logging、java.xml、java.transaction.xa 等模块的公开 API。

它既适用于模块化源码，也适用于非模块化（classpath）源码。

需要注意命名冲突：模块导入相当于批量导入，如果两个模块导出了同名类，就必须用单类型导入显式指定。例如：

java
import module java.base;
import module java.sql;

这个特性适合脚本、示例、原型这类追求简洁的场景。大型工程里仍建议显式导入，避免依赖关系变得模糊。

编译器的处理方式是：把文件内容隐式包在一个最终的顶层类中（该类不能实现接口），并自动导入 java.base 模块导出的所有包。因此 IO、List、ArrayList 等都可以直接使用。

java.lang.IO 是专门为这种写法准备的工具类，提供了：

  • IO.print(...) / IO.println(...)
  • IO.readln(...)：从标准输入读取一行

void main() {

启动器选择 main 方法的优先级如下：

  1. static void main(String[])
  2. static void main()
  3. 实例方法 void main(String[])

如果选中的是实例方法，启动器会先调用该类的无参构造器。注意返回值必须是 void，int main 之类不会被视为入口。

二、并发编程 ​

JEP 506：作用域值 ScopedValue（正式） ​

ThreadLocal 用起来简单，但有几个老问题：

  • 必须手动 remove()，否则线程池场景下容易内存泄漏、数据串线；
  • 每个线程一份副本，数量多了内存开销大；
  • 子线程默认拿不到父线程的值（InheritableThreadLocal 又有各种坑）；
  • 值是可变的，任意代码都能改。

ScopedValue（作用域值） 提供了一种不可变、有明确生命周期、可自动继承的数据传递方式。它经过多轮预览后，在 JDK 25 正式转正。

java
public final class RequestContext {

    public static final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

    public static void handle(Request request) {
        ScopedValue.where(CURRENT_USER, request.user())
                   .run(() -> process(request));
    }

    private static void process(Request request) {
        User user = CURRENT_USER.get();
        // 处理业务
    }
}

几个关键特性：

  • 不可变：绑定期间值不能被修改，只能通过嵌套 where(...) 重新绑定；
  • 嵌套绑定：内层绑定只在内层作用域有效，退出后自动恢复外层值；
  • 自动解绑：run/call 结束（包括异常退出）后绑定自动失效，不需要 remove()；
  • 结构化继承：由 StructuredTaskScope 创建的子任务会自动继承作用域值；
  • 读取开销低：查找是 O(1) 级别，适合高频读取。

嵌套绑定的行为：

java
ScopedValue.where(USER, "alice").run(() -> {
    ScopedValue.where(USER, "bob").run(() -> {
        System.out.println(USER.get());   // bob
    });
    System.out.println(USER.get());       // alice
});

JEP 505：结构化并发（第五次预览） ​

结构化并发把"一组相关子任务"看作一个整体：父任务等待所有子任务结束，任何一个失败都会取消其余任务，从而避免线程泄漏和错误被吞掉。

JDK 25 是第五次预览，API 做了较大调整：

  • StructuredTaskScope 变成两个类型参数：StructuredTaskScope<T, R>
    • T：子任务返回值类型；
    • R：join() 的返回类型。
  • join() 直接返回 R，不再需要额外从子任务里取值；
  • 子任务类型 Subtask<T> 实现了 Supplier<T>；
  • 通过 Joiner 指定"等待策略"。

最常见的用法是"全部成功才继续"：

java
record Response(User user, List<Order> orders) {}

Response handle(long userId) throws Exception {
    try (var scope = StructuredTaskScope.open()) {
        Subtask<User> userTask = scope.fork(() -> userService.find(userId));
        Subtask<List<Order>> orderTask = scope.fork(() -> orderService.listByUser(userId));

        scope.join();   // 任一子任务失败：取消另一个，并抛出 FailedException

        return new Response(userTask.get(), orderTask.get());
    }
}

StructuredTaskScope.open() 等价于使用默认的 Joiner.awaitAllSuccessfulOrThrow()，join() 返回 Void（即 null），结果通过各个 Subtask.get() 获取。

注意：fork 接收的是 Supplier，子任务不能直接抛出受检异常。如果底层方法会抛受检异常，需要在 lambda 内包装成运行时异常。

常用的 Joiner：

Joiner语义join() 返回
awaitAllSuccessfulOrThrow()等待全部成功，结果自行从 Subtask 取Void
allSuccessfulOrThrow()等待全部成功并收集结果List<T>
anySuccessfulResultOrThrow()任意一个成功即可，取消其余T
anySuccessfulOrThrow()任意一个成功，返回该子任务Subtask<T>
awaitAll()等待全部结束，无论成功失败List<Subtask<T>>

"取最快成功的那个"——典型的双活、竞速场景：

java
String fetchFastest() throws Exception {
    try (var scope = StructuredTaskScope.open(Joiner.anySuccessfulResultOrThrow())) {
        scope.fork(() -> fetch("https://primary.example.com"));
        scope.fork(() -> fetch("https://backup.example.com"));

        return scope.join();   // 返回最先成功的结果，另一个被取消
    }
}

三、核心库 ​

JEP 502：稳定值 StableValue（预览） ​

StableValue 用来表达一种"延迟初始化，但一旦设置就永不改变"的值。它结合了懒加载和不可变两个优点，并且 JIT 可以把它当作常量来优化。

java
private static final StableValue<Path> CONFIG_PATH = StableValue.of();

Path configPath() {
    return CONFIG_PATH.orElseSet(
            () -> Path.of(System.getProperty("app.config", "config.yml")));
}

核心 API：

方法说明
StableValue.of()创建未设置值的实例
StableValue.of(T)创建已设置值的实例
StableValue.supplier(Supplier)返回一个稳定 Supplier，首次 get() 时计算并缓存
StableValue.function(Set, Function)按允许的输入集合缓存函数结果
StableValue.intFunction(int, IntFunction)按 [0, size) 范围缓存函数结果
StableValue.list(int, IntFunction)创建惰性计算的不可变 List
StableValue.map(Set, Function)创建惰性计算的不可变 Map
trySet(T)尝试设置，已设置则返回 false
setOrThrow(T)设置值，已设置则抛 IllegalStateException
orElseSet(Supplier)未设置则原子地计算并设置
orElse(T) / orElseThrow()取值或提供默认值 / 抛异常
isSet()是否已设置

几个实用例子：

java
// 延迟初始化一个昂贵对象

private static final Map<String, Color> COLORS =
        StableValue.map(Set.of("red", "green", "blue"), Color::parse);

JEP 507：基本类型模式匹配（第三次预览） ​

JDK 21 的模式匹配主要面向引用类型。JEP 507 把 instanceof 和 switch 的模式匹配扩展到基本类型，并且支持安全收窄：只有当值能被目标类型精确表示时才匹配。

java
int value = 300;

if (value instanceof byte b) {
    System.out.println("可以放进 byte：" + b);
} else {
    System.out.println("超出 byte 范围");
}

300 超出 byte 范围，所以不匹配。这种写法比 value >= Byte.MIN_VALUE && value <= Byte.MAX_VALUE 更直观，也更不容易写错边界。

switch 中可以做多级收窄：

java
static String classify(int value) {
    return switch (value) {
        case byte b  -> "byte 范围: " + b;
        case short s -> "short 范围: " + s;
        default      -> "int 范围: " + value;
    };
}

JDK 25 的 switch 选择器还支持 long、float、double 和 boolean。匹配规则要点：

  • 收窄转换必须是精确的，有信息丢失就不匹配；
  • 基本类型模式不匹配 null；
  • 模式按书写顺序依次尝试，范围小的类型要放在前面；
  • 对 float/double 来说，只有能精确表示的值才会匹配。

这个特性目前仍是预览，需要 --enable-preview。

JEP 510：密钥派生函数 API（正式） ​

以前在 Java 里做 HKDF 之类的密钥派生，要么自己拼 HMAC，要么依赖 BouncyCastle。JDK 25 新增了标准的 javax.crypto.KDF API，首先支持 HKDF：

  • HKDF-SHA256
  • HKDF-SHA384

AlgorithmParameterSpec params = HKDFParameterSpec.ofExtract()

        .addSalt(salt)
        .thenExpand(info, 32);

SecretKey aesKey = hkdf.deriveKey("AES", params);

四、JVM 与性能 ​

JEP 519：紧凑对象头（正式） ​

HotSpot 每个对象都有一个对象头，传统布局在 64 位下占 12 字节（Mark Word 8 字节 + 类型指针 4 字节）。JDK 25 的紧凑对象头把它压缩到 8 字节。

对于小对象密集的应用（大量 Integer、String、DTO、集合节点等），收益非常可观，官方给出的数据是堆占用最多可减少约 22%。

该特性在 JDK 24 还是实验性的，JDK 25 转为正式产品特性，不再需要 -XX:+UnlockExperimentalVMOptions：

bash
java -XX:+UseCompactObjectHeaders -jar app.jar
1

它不是默认开启的，需要显式启用。启用前建议做完整的兼容性和性能压测，尤其是依赖对象内存布局的库（如某些序列化、缓存、内存分析工具）。

JEP 521：分代 Shenandoah（正式） ​

Shenandoah 是一款低停顿 GC。此前它只有单代模式，所有对象混在一起回收。JDK 25 的分代 Shenandoah 转为正式产品特性，可以区分新生代和老年代，更符合"大部分对象朝生夕死"的分代假说，通常能带来更好的吞吐和更稳定的停顿。

启用方式：

bash
java -XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational -jar app.jar
1

注意两点：

  • 默认仍然是单代模式，需要显式指定 ShenandoahGCMode=generational；
  • 转正后不再需要 -XX:+UnlockExperimentalVMOptions。

JEP 514：AOT 命令行简化 ​

JDK 24 引入了 AOT 类加载与链接（Leyden 项目的一部分），但流程比较繁琐，需要先 record 再 create：

bash
# JDK 24：两步
java -XX:AOTMode=record -XX:AOTConfiguration=app.aotconf -cp app.jar com.example.App
java -XX:AOTMode=create -XX:AOTConfiguration=app.aotconf -XX:AOTCache=app.aot -cp app.jar
1
2
3

JDK 25 简化为一步：

bash
# 1. 训练运行，同时生成 AOT 缓存
java -XX:AOTCacheOutput=app.aot -cp app.jar com.example.App

# 2. 使用缓存启动，跳过大量类加载、链接和验证
java -XX:AOTCache=app.aot -cp app.jar com.example.App
1
2
3
4
5

对于启动时间敏感的 CLI 工具、Serverless 函数、短生命周期服务，这个优化很有价值。AOT 缓存与 JDK 版本、启动参数、classpath 相关，升级 JDK 或改动依赖后需要重新生成。

JEP 515：AOT 方法剖析 ​

仅靠 AOT 缓存可以加速类加载，但 JIT 仍然缺少"哪些方法热"的信息，启动初期只能解释执行或做低质量编译。

JEP 515 在 AOT 训练运行期间顺带收集方法执行剖析数据（调用次数、分支走向等），并存入 AOT 缓存。使用缓存启动时，JIT 可以直接利用这些历史画像，对热方法更早、更准地编译。

它不需要新的命令行参数，复用 JEP 514 的 AOT 工作流即可。两者配合，可以明显缩短应用的"预热期"。

JEP 508：Vector API（第十次孵化） ​

Vector API 用于把 SIMD 指令显式暴露给 Java 程序，适合数值计算、图像处理、加解密等数据并行场景。JDK 25 是第十次孵化，API 仍在演进。

java
import jdk.incubator.vector.FloatVector;

static void add(float[] a, float[] b, float[] c) {
    var species = FloatVector.SPECIES_PREFERRED;
    for (int i = 0; i < a.length; i += species.length()) {
        var va = FloatVector.fromArray(species, a, i);
        var vb = FloatVector.fromArray(species, b, i);
        va.add(vb).intoArray(c, i);
    }
}

javac --add-modules jdk.incubator.vector Main.java

五、JFR 增强 ​

JFR（Java Flight Recorder）在 JDK 25 获得了三项增强，日常排查性能问题时很有用。

JEP 518：协作采样（正式） ​

此前 JFR 的方法采样（如 jdk.ExecutionSample）依赖安全点轮询，采样点容易偏向安全点位置，导致火焰图失真，同时也会带来额外的安全点开销。

JEP 518 改为协作采样：由采样线程与 Java 线程协作完成栈采集，减少安全点偏差，让采样结果更接近真实执行分布。这是内部实现改动，无需任何参数，升级即可受益。

JEP 509：CPU 时间剖析（实验） ​

传统 JFR 采样基于墙钟时间，无法区分"线程在跑"还是"线程在等"。JEP 509 新增了基于 CPU 时间的采样事件 jdk.CPUTimeSample，能更准确地定位真正消耗 CPU 的代码。

启用方式：

bash
java -XX:StartFlightRecording=jdk.CPUTimeSample#enabled=true MyApp
1

限制：

  • 目前仅支持 Linux；
  • 在 JDK 25 中仍是实验特性；
  • 依赖操作系统的 CPU 时间采样能力，容器或受限环境下可能不可用。

JEP 520：方法计时与追踪（正式） ​

有时我们只关心某几个方法的调用次数和耗时，或者想看清某个方法到底被谁调用。JEP 520 新增两个事件：

  • jdk.MethodTiming：统计指定方法的调用次数和总耗时；
  • jdk.MethodTrace：记录指定方法的调用栈。

可以在启动 JFR 时通过过滤器指定目标方法：

bash
# 统计 com.example 包下方法的调用次数与耗时
java -XX:StartFlightRecording:method-timing=com.example.* MyApp

# 追踪 com.example 包下方法的调用栈
java -XX:StartFlightRecording:method-trace=com.example.* MyApp
1
2
3
4
5

两个事件也支持在 JFR 配置文件（.jfc）中开启。由于会记录方法级信息，开销高于普通采样，建议只在针对性排查时短时间开启。

六、移除项 ​

JEP 503：移除 32 位 x86 端口 ​

JDK 25 移除了对 32 位 x86（i386/x86-32）平台的源码和构建支持。原因很直接：该平台近年来几乎没有实际使用，维护成本却一直存在。

影响范围：

  • 不再提供 32 位 x86 的 JDK 构建；
  • 仍然支持 64 位 x86（x86-64）、AArch64、RISC-V 等平台；
  • 极少数仍运行在 32 位 x86 上的遗留系统需要停留在 JDK 21 或迁移到 64 位环境。

升级与使用建议 ​

1. 预览特性要成对开启

JDK 25 中仍有预览/孵化特性，编译和运行都需要显式开启：

bash
javac --release 25 --enable-preview Main.java
java --enable-preview Main
1
2

预览 API 可能在下一个版本发生变化，不建议在生产代码中依赖。

2. 值得优先尝试的正式特性

  • ScopedValue：替换请求上下文中的 ThreadLocal，代码更干净，也不用担心泄漏；
  • 灵活构造函数体：把参数校验提前，减少"父类构造完才发现参数非法"的问题；
  • 紧凑源文件 + 实例 main：写示例、脚本、教学代码非常方便；
  • 模块导入声明：小项目和演示代码可以少写大量 import；
  • 紧凑对象头与分代 Shenandoah：内存和 GC 层面的收益，建议压测后启用。

3. AOT 缓存适合启动敏感型应用

CLI、Serverless、短生命周期服务可以尝试 -XX:AOTCacheOutput / -XX:AOTCache，配合 JDK 25 的 AOT 方法剖析，能明显缩短启动和预热时间。缓存与 JDK 版本、启动参数强相关，记得纳入构建流程统一生成。

4. 升级路径

从 JDK 21 升级到 25 相对平滑，主要关注点：

  • 检查是否有 32 位 x86 部署；
  • 检查依赖库是否使用了被移除或变更的内部 API；
  • 用 jdeps、jdeprscan 扫描依赖；
  • 对 GC 参数、对象布局敏感的中间件做专项压测；
  • 预览特性在升级后需要重新验证语法与 API 变化。
